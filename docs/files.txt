# Today's Progress — Building the Word Index

## What I Worked On

Today I improved the `buildindex()` function of my file search engine. The goal was to make the program properly read a file line-by-line, extract individual words, and store their frequencies in the `wordfrequency` map.

---

## 1. Learned How `getline()` Works

I learned that:

```cpp
getline(file, line);
```

reads characters from the file until it encounters a newline and stores the contents of that line in the `line` string.

For example, if the file contains:

```text
hello world
this is a file
```

successive calls to `getline()` give:

```text
line = "hello world"
line = "this is a file"
```

I also learned that `getline()` returns a value that can be used to determine whether reading was successful.

This allows:

```cpp
while(getline(file, line)){
    // process line
}
```

to stop automatically when the end of the file is reached.

---

## 2. Fixed the Empty-Line Problem

Previously, the loop used:

```cpp
while(line != "" && line != "File is not open")
```

The problem was that an empty line is valid file content. Therefore, an empty line should not mean that the file has ended.

For example:

```text
hello world


how are you
```

The program should continue reading after the empty lines.

The solution was to use the return value of `getline()` to detect EOF instead of using an empty string.

---

## 3. Changed `readfile()`

`readfile()` was changed so that it returns a `bool` and receives the line by reference:

```cpp
bool Filereader::readfile(string filename, string &line){
    if (!file.is_open()) {
        file.open(filename);
    }

    if (!file.is_open()) {
        return false;
    }

    if(getline(file,line)){
        return true;
    }

    return false;
}
```

The two pieces of information are now separated:

* `line` contains the actual line read from the file.
* `bool` tells `buildindex()` whether the read was successful.

The `&` means that `readfile()` modifies the original `line` variable from `buildindex()`.

---

## 4. Learned About `<cctype>`

I learned about the `<cctype>` library, which provides functions for working with individual characters.

For this project I used:

```cpp
isspace()
ispunct()
```

`isspace()` checks whether a character is whitespace, such as a space or tab.

`ispunct()` checks whether a character is punctuation.

This allowed the word parser to treat spaces and punctuation as word separators.

---

## 5. Improved Word Parsing

Previously, the program only checked for:

```cpp
x != ' '
```

This meant that punctuation remained attached to words.

For example:

```text
hello, world!
```

could become:

```text
hello,
world!
```

After using:

```cpp
if(!isspace(x) && !ispunct(x)){
    word = word + x;
}
```

punctuation and whitespace are treated as separators.

The program can therefore extract:

```text
hello
world
```

instead of including the punctuation.

---

## 6. Handled Multiple Spaces

The program now correctly handles input such as:

```text
hello    how     are    you
```

The inner condition:

```cpp
if(word != ""){
    wordfrequency[word]++;
    word = "";
}
```

prevents an empty string from being added to the index when multiple separators occur consecutively.

Without this check, the program could accidentally execute:

```cpp
wordfrequency[""]++;
```

---

## 7. Fixed the Last Word of Each Line

Previously, a word was only stored when a separator was encountered.

For example:

```text
hello world
```

`hello` was followed by a space, so it was stored.

But `world` reached the end of the line without encountering a space, so it wasn't stored.

I fixed this by checking after the `for` loop:

```cpp
if(word != ""){
    wordfrequency[word]++;
    word = "";
}
```

This makes sure the final word of every line is also added to the index.

---

## 8. Important Bug I Found

I initially had:

```cpp
while(readfile(filename, line)){
    // process line

    line = readfile(filename, line);
}
```

This was incorrect because `readfile()` returns a `bool`, not a `string`.

More importantly, the `while` condition was already reading the next line. Calling `readfile()` again at the bottom would cause every other line to be skipped.

Therefore, the extra call was removed.

The correct structure is:

```cpp
while(readfile(filename, line)){
    // process the line
}
```

---

## Final Structure

The indexing process now works conceptually like this:

```text
Open file
    ↓
Read a line using readfile()
    ↓
getline() puts the line into `line`
    ↓
Process each character
    ↓
Build a word
    ↓
Whitespace/punctuation encountered
    ↓
Store word in wordfrequency
    ↓
Store final word of the line
    ↓
Read next line
    ↓
EOF → readfile() returns false
    ↓
Stop
```

# Milestone 1 — Basic File Search Engine

## Overview

The first milestone of the File Search Engine project has been successfully completed.

The goal of this stage was to build the basic foundation of the search engine: **open a text file, read its contents, build a word-frequency index, and search for individual words using that index.**

## What We Built

### 1. File Opening

We implemented functionality to open a file provided by the user using C++ `ifstream`.

The program checks whether the file was successfully opened before attempting to read its contents.

### 2. File Reading

We created the `readfile()` function to read the file line by line using `getline()`.

The function also handles opening the file when necessary and returns a boolean value indicating whether a line was successfully read.

### 3. Word Tokenization

Inside `buildindex()`, each line is processed character by character.

Characters are used to construct individual words while spaces and punctuation are treated as separators.

This allowed us to extract individual words from the file instead of treating an entire line as one string.

### 4. Building the Word Index

We created a hash table using:

```cpp
unordered_map<string, int> wordfrequency;
```

The structure stores:

```text
word → frequency
```

For example:

```text
computer → 5
system   → 12
program  → 8
```

Every time a word is encountered, its frequency is incremented.

### 5. Making `buildindex()` Return a Boolean

We changed `buildindex()` from a `void` function to a boolean-returning function.

It now communicates whether the indexing operation succeeded:

```text
true  → index successfully built
false → indexing failed
```

This allows `main()` to control whether searching should proceed.

### 6. Implementing Word Search

We implemented `searchword()` using the `unordered_map::find()` function.

Instead of traversing the entire map manually, we perform a hash-based lookup:

```cpp
auto it = wordfrequency.find(word);
```

If:

```cpp
it != wordfrequency.end()
```

the word exists in the index.

Its frequency can then be obtained using:

```cpp
it->second
```

If the iterator equals:

```cpp
wordfrequency.end()
```

the word was not found.

### 7. Separating Indexing and Searching

We also made an important architectural improvement.

Initially, `searchword()` was responsible for calling `buildindex()` itself. We recognized that this would rebuild the entire index every time a new word was searched.

Instead, `main()` now controls the process:

```text
main()
 │
 ├── buildindex(filename)
 │
 └── searchword(word)
```

This means the file is indexed once and multiple words can subsequently be searched efficiently.

## Final Architecture

The completed Stage 1 pipeline is:

```text
File
 ↓
readfile()
 ↓
buildindex()
 ↓
unordered_map<string, int>
 ↓
searchword()
 ↓
find(word)
 ↓
Frequency / Not Found
```

# FileFinder Project — Feature 1

## Current Goal

Build a **portable and scalable C++ FileFinder** that allows the user to provide a filename and searches for matching files using the C++ standard library.

The user should eventually only need to provide:

```text
filename
```

The FileFinder should handle the filesystem traversal itself.

---

## Current Class Design

We created a `FileFinder` class with the filename stored as a private member:

```cpp
class FileFinder
{
private:
    std::string filename;

public:
    FileFinder(const std::string& filename)
        : filename(filename)
    {
    }

    void findfiles();
};
```

### Why `filename` is private

The filename is an internal property of the `FileFinder` object. Keeping it private provides encapsulation and allows us to control access later.

We decided **not to use `protected` just for possible future inheritance**. If derived classes eventually need access, we can provide controlled protected functions later.

---

## Why We Use a Constructor

The constructor initializes the filename when the object is created:

```cpp
FileFinder finder("main.cpp");
```

This creates an object whose internal state is:

```text
finder
 └── filename = "main.cpp"
```

A `FileFinder` without a target filename doesn't make much sense, so requiring the filename during construction puts the object into a useful initial state.

We use an initializer list:

```cpp
FileFinder(const std::string& filename)
    : filename(filename)
{
}
```

---

# First Feature: Recursive Filename Search

The basic implementation is:

```cpp
void FileFinder::findfiles()
{
    for (const auto& entry : fs::recursive_directory_iterator("."))
    {
        if (entry.is_regular_file() &&
            entry.path().filename() == filename)
        {
            std::cout << "Found: "
                      << entry.path().string()
                      << std::endl;
        }
    }
}
```

Required headers:

```cpp
#include <iostream>
#include <filesystem>
#include <string>
#include "filefinder.h"

namespace fs = std::filesystem;
```

---

# `std::filesystem`

We are using the C++ standard filesystem library instead of Windows-specific APIs.

This is important because the long-term goal is to make the FileFinder portable across systems such as:

```text
Windows
Linux
macOS
```

The filesystem namespace is shortened with:

```cpp
namespace fs = std::filesystem;
```

so we can write:

```cpp
fs::recursive_directory_iterator
```

instead of:

```cpp
std::filesystem::recursive_directory_iterator
```

---

# `recursive_directory_iterator`

The main traversal mechanism is:

```cpp
fs::recursive_directory_iterator(".")
```

It starts at `"."`, where `"."` means the **current working directory**.

It then automatically enters subdirectories.

For example:

```text
Project/
├── main.cpp
├── test.cpp
├── src/
│   ├── app.cpp
│   └── utils/
│       └── helper.cpp
└── docs/
    └── notes.txt
```

A recursive iterator can visit:

```text
main.cpp
test.cpp
src/
src/app.cpp
src/utils/
src/utils/helper.cpp
docs/
docs/notes.txt
```

The important distinction:

```cpp
fs::directory_iterator(".")
```

only examines the current directory.

```cpp
fs::recursive_directory_iterator(".")
```

also enters subdirectories recursively.

---

# Understanding the Range-Based For Loop

We use:

```cpp
for (const auto& entry :
     fs::recursive_directory_iterator("."))
```

There are three important parts.

### `entry`

`entry` represents the **current filesystem entry** being visited.

Its actual type is essentially:

```cpp
std::filesystem::directory_entry
```

It can represent things such as:

```text
file
directory
symbolic link
```

### `auto`

Instead of explicitly writing:

```cpp
std::filesystem::directory_entry
```

we let C++ determine the type automatically:

```cpp
auto
```

### `&`

The `&` means `entry` is a **reference** instead of a copy.

We don't need to make a separate copy of every filesystem entry because we're only inspecting them.

### `const`

We only want to read the entry, not modify it.

Therefore:

```cpp
const auto& entry
```

means approximately:

> Give me a read-only reference to the current filesystem entry.

---

# `entry.path()`

`entry.path()` gives the path of the filesystem entry currently being visited.

For example, if the iterator reaches:

```text
C:\Projects\src\main.cpp
```

then:

```cpp
entry.path()
```

represents:

```text
C:\Projects\src\main.cpp
```

Its type is:

```cpp
std::filesystem::path
```

---

# `entry.path().filename()`

We can extract only the filename from the path:

```cpp
entry.path().filename()
```

For:

```text
C:\Projects\src\main.cpp
```

we get:

```text
main.cpp
```

Therefore:

```cpp
entry.path()
```

means:

> Where is this filesystem entry?

while:

```cpp
entry.path().filename()
```

means:

> What is the name of this filesystem entry?

---

# `is_regular_file()`

A filesystem entry can be a directory or a file.

We use:

```cpp
entry.is_regular_file()
```

to determine whether the current entry is a **normal/regular file**.

Examples of regular files:

```text
main.cpp
notes.txt
photo.jpg
data.csv
program.exe
```

A directory such as:

```text
src/
```

is not a regular file.

Therefore our condition:

```cpp
entry.is_regular_file() &&
entry.path().filename() == filename
```

means:

> Is this a normal file, and does its filename match the filename we're searching for?

If both are true, we found the file.

# Important Design Decisions So Far

1. Use **standard C++ filesystem**, not Windows-specific APIs.
2. Store the target filename as a **private member** of `FileFinder`.
3. Require the filename when constructing the object.
4. Use `std::filesystem::recursive_directory_iterator` for recursive traversal.
5. Start searching from `"."` for the first implementation.
6. Only consider `is_regular_file()` entries.
7. Compare `entry.path().filename()` with the target filename.
8. Print the complete path when a match is found.
9. Keep `FileFinder` implementation separate from `main()`.

# 2. New requirement

The next goal is no longer just:

```text
User chooses directory
        ↓
Search that directory
        ↓
Search its subdirectories
```

We want:

```text
Find a file across the system
        ↓
Discover appropriate search roots
        ↓
Search each root recursively
```

The problem is that different operating systems have different concepts of filesystem roots.

### Windows

```text
C:\
D:\
E:\
...
```

### Linux

Usually one filesystem hierarchy beginning at:

```text
/
```

but there can also be mounted filesystems.

### macOS

Also has a Unix-style root:

```text
/
```

Therefore, the common searching algorithm can be portable, but **discovering the roots is OS-specific**.

---

# 3. Search-root abstraction

We introduced the idea of a **search root**.

A search root is simply:

> The directory from which our recursive search begins.

For example:

```text
C:\
```

can be a search root on Windows.

The important design idea is that `FileFinder` should not need to know how Windows, Linux, or macOS discovers its roots.

Instead:

```text
FileFinder
    |
    └── getSearchRoots()
            |
            ├── Windows implementation
            ├── Linux implementation
            └── macOS implementation
```

This is called **abstraction**: the common search logic doesn't need to know the platform-specific details.

---

# 4. We chose inheritance

Instead of putting Windows/Linux/macOS code everywhere using `#ifdef`, we decided to use inheritance.

The design is:

```text
                 FileFinder
                     |
        ┌────────────┼────────────┐
        ↓            ↓            ↓
 WinFileFinder  LinuxFileFinder  MacFileFinder
```

`FileFinder` contains the functionality common to all operating systems.

The derived classes handle the platform-specific part.

---

# 5. Base class

Our current base class is:

```cpp
class FileFinder {
protected:
    std::string filename;

public:
    FileFinder(const std::string& filename) {
        this->filename = filename;
    }

    void findfiles();

    virtual std::vector<fs::path> getSearchRoots() = 0;
};
```

The base class stores:

```cpp
std::string filename;
```

because every type of FileFinder needs to know which file it is searching for.

It also contains:

```cpp
void findfiles();
```

because the actual searching algorithm is common to all operating systems.

---

# 6. Pure virtual function

The important new part is:

```cpp
virtual std::vector<fs::path> getSearchRoots() = 0;
```

We learned that:

```cpp
virtual
```

means the function can be overridden by derived classes and supports runtime polymorphism.

The:

```cpp
= 0
```

makes it a **pure virtual function**.

This means:

> `FileFinder` requires every concrete derived class to provide its own `getSearchRoots()` implementation.

Therefore `FileFinder` becomes an **abstract class**.

We cannot directly create:

```cpp
FileFinder finder(...);
```

Instead, we create a concrete derived class such as:

```cpp
WinFileFinder finder(...);
```

# 7. Derived classes


```cpp

public:
```

```cpp
};
```

The important thing is that all three classes share the same interface:

```cpp

```

but each one will eventually implement it differently.

---

# 8. What `override` means

We learned that:

```cpp
std::vector<fs::path> getSearchRoots() override;
```

means:

> "This function is supposed to override a virtual function from the base class. Compiler, please verify that I actually did it correctly."

For example, if the base class has:

```cpp
virtual std::vector<fs::path> getSearchRoots() = 0;
```

and we accidentally write:

```cpp
std::vector<fs::path> getSearchRoot() override;
```

the compiler will complain because `getSearchRoot()` does not actually override `getSearchRoots()`.

So `override` provides compile-time safety.

## 1. What I Learned

Today I continued developing the portable **FileFinder** project and focused on how the program can work differently on different operating systems.

### Inheritance and OS-specific classes

I understood that the base `FileFinder` class contains the functionality that is common to all operating systems, while separate derived classes handle OS-specific behavior.

```text
                    FileFinder
```

The common searching algorithm belongs to `FileFinder`, while each derived class provides its own implementation for discovering the directories that should be searched.

### Virtual functions

I learned that a function is made `virtual` when we want derived classes to provide their own implementation and have C++ select the appropriate implementation through polymorphism.

In this project:

```cpp
void findfiles();
```

is common to all operating systems, so it belongs to the base class and does not need to be virtual.

On the other hand:

```cpp
virtual std::vector<fs::path> getSearchRoots() = 0;
```

is OS-specific, so it is virtual and pure virtual.

This means every derived class must implement its own `getSearchRoots()`.

The design is therefore:

```text
FileFinder
 |
 +-- findfiles()             → common searching algorithm
 |
 +-- getSearchRoots()        → OS-specific, virtual
        |
        +-- Windows
        +-- Linux
        +-- macOS
```

I also understood that when `findfiles()` calls `getSearchRoots()`, the appropriate derived-class implementation can be selected through runtime polymorphism.

## 2. OS Identification

I learned that the operating system can be identified at compile time using preprocessor macros.

For example:

```cpp
#ifdef _WIN32
    // Windows
#elif defined(__linux__)
    // Linux
#elif defined(__APPLE__)
    // macOS
#endif
```

The OS-selection logic should be placed in the running/application code, such as `main.cpp`, rather than putting OS-selection logic inside the base `FileFinder` class.

## 4. Understanding DWORD

`DWORD` means **Double Word** and represents a **32-bit unsigned integer**.

I used:

```cpp
DWORD drives = GetLogicalDrives();
```

`GetLogicalDrives()` returns information about which logical drives are currently available.

The important idea is that the 32 bits of the `DWORD` are used as flags.

Each bit corresponds to a drive:

```text
Bit 0 → A:
Bit 1 → B:
Bit 2 → C:
Bit 3 → D:
...
Bit 25 → Z:
```

## 5. Bit Manipulation and Bit Masks

I learned how this expression works:

```cpp
drives & (1 << (drive - 'A'))
```

First:

```cpp
drive - 'A'
```

converts the drive letter into a number representing its bit position.

For example:

```text
'A' - 'A' = 0
'B' - 'A' = 1
'C' - 'A' = 2
'D' - 'A' = 3
```

Then:

```cpp
1 << (drive - 'A')
```

moves the `1` to the appropriate bit position.

For C:

```text
'C' - 'A' = 2

1 << 2

00000100
```

This creates a **bit mask**.

Then the bitwise AND:

```cpp
drives & mask
```

checks whether that particular bit is set.

If the result is non-zero, that drive exists.

This gave me a practical introduction to **bitwise operators and bit masks**, which are important concepts in systems programming.

## 7. Windows `getSearchRoots()` Implemented

I implemented the Windows-specific root discovery function:

```cpp
#include <windows.h>
#include <vector>
#include <string>
#include "filefinder.h"

std::vector<fs::path> WinFileFinder::getSearchRoots() {

    std::vector<fs::path> roots;
    DWORD drives = GetLogicalDrives();

    for (char drive = 'A'; drive <= 'Z'; drive++) {

        if (drives & (1 << (drive - 'A'))) {

            std::string root = std::string(1, drive) + ":\\";
            roots.push_back(root);
        }
    }

    return roots;
}
```

This function:

1. Gets the available logical drives from Windows.
2. Checks drives from `A` to `Z`.
3. Uses bit manipulation to determine whether each drive exists.
4. Creates paths such as `C:\`, `D:\`, etc.
5. Stores them in a `std::vector<fs::path>`.
6. Returns the vector to the base-class searching algorithm.
